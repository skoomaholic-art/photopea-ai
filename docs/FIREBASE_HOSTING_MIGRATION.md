# Poster Editor: бесплатный Firebase Hosting

Этот набор файлов **готовит** перенос клиентской части на Firebase Hosting (Spark). До подключения собственного Firebase-проекта и GitHub credentials развертывание не выполняется. Текущий GitHub Pages и Cloudflare Worker не изменяются.

## Почему именно Hosting

Poster Editor уже собирается в статический каталог `dist/` командами `npm run build:vendor` и `npm run build:static`. Firebase Hosting в тарифе **Spark** размещает статический сайт без платежной карты в пределах бесплатных квот. Не путать с Firebase **App Hosting** и Cloud Run: они требуют тариф Blaze и привязку биллинга. **Не включать Blaze**, не привязывать платежную карту и не создавать платные ресурсы.

Актуальные ограничения уточнять на https://firebase.google.com/pricing. Если бесплатная квота Hosting закончится, доступность может быть ограничена; автоматического платного превышения на Spark нет.

## Что переезжает

- HTML/CSS/JS, локальный экспорт PNG/ZIP/JSON, Photopea, ТОП10 и Паровозик.
- Уже существующий клиентский URL API из `<meta name="poster-api">` пока сохраняется: `https://skoomaholic.alexandr-petrossov.workers.dev`. Cloudflare Worker **не переносится на Google** этим шагом. Поиск изображений и удалённые функции продолжат зависеть от него. Платные AI-запросы не включаем.
- GitHub Pages остается параллельным работающим адресом и запасным вариантом до успешного переключения.

## Однократное подключение владельцем

1. На https://console.firebase.google.com/ создать проект или выбрать существующий, оставить **Spark**, выбрать **Hosting** (не App Hosting). Сохранить ID проекта.
2. В GitHub репозитории открыть `Settings → Secrets and variables → Actions`. Сначала добавить **секрет** `FIREBASE_SERVICE_ACCOUNT_POSTER_EDITOR` с JSON специально созданного сервисного аккаунта для Firebase Hosting. Не вставлять ключ ни в репозиторий, ни в чат. Наиболее безопасный стандартный способ выдачи учетных данных описан в https://firebase.google.com/docs/hosting/github-integration: команда `firebase init hosting:github` автоматически создает сервисный аккаунт и GitHub secret. Если использовать этот способ, согласовать имя сгенерированного секрета с именем в нашем `firebase-hosting.yml` (поменять имя в workflow на фактически созданное), а созданные CLI дополнительные workflow не дублировать.
3. После наличия рабочего секрета создать в GitHub `Actions → Variables` переменную `FIREBASE_PROJECT_ID` с точным ID проекта. Отсутствующая переменная специально блокирует запуск нашего Firebase workflow.
4. Когда PR с этой конфигурацией будет слит в `main`, запустить `Deploy Firebase Hosting (Spark)` в `Actions` через `Run workflow`. После успешного выполнения ожидаемый адрес `https://<project-id>.web.app`; фактический адрес смотреть в результате Firebase Hosting.
5. Проверить на новом адресе все редакторы, поиск и API. Если Worker ограничивает CORS по Origin, отдельно разрешить фактический origin `https://<project-id>.web.app` и при необходимости `https://<project-id>.firebaseapp.com`, не открывая wildcard. До подтвержденной работы **не отключать** GitHub Pages.

## Особо важно: данные браузера

Архив логотипов, Asset Manager, автосохраненные макеты и PSD в браузере находятся в IndexedDB, привязанной к **исходному origin** `skoomaholic-art.github.io`. На `<project-id>.web.app` они **не появятся автоматически**. Не очищать данные старого сайта и не удалять GitHub Pages. Перед окончательным переездом нужно добавить или воспользоваться явным механизмом экспорта/импорта локального архива и проектов. Функция «Сохранить проект» сохраняет отдельную композицию, но это **не означает** полного переноса всех архивных логотипов.

## Безопасность и стоимость

- Этот workflow публикует только allowlisted `dist/`, а не сервер, тесты, `.env` или ключи.
- Секреты и ключи API остаются на своем сервере/Worker, не помещаются в HTML.
- Включение платежного аккаунта Google Cloud автоматически может перевести проект на Blaze. Не привязывать биллинг ради этой миграции.
